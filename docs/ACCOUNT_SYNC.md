# Optional account and progress sync

`/settings/sync` remains usable without configuration and makes no cloud requests
until the user requests sign-in. Practice remains in browser storage. Sync is a
manual snapshot transfer, not background synchronization or automatic merging.

## Provisioning (deployment owner)

1. Choose a Supabase project yourself. No project, paid service, email or database
   has been provisioned by this implementation.
2. Review `supabase/migrations/account_sync.sql` and execute it once in the SQL
   editor. Alternatively install the Supabase CLI, discover its commands with
   `supabase --help` and `supabase migration --help`, run
   `supabase migration new account_sync`, and copy this script into the generated
   migration. The checked-in unversioned SQL is a provisioning template, not an
   applied migration history. The CLI was unavailable during implementation.
3. Enable Email Auth. Disable anonymous sign-ins. Configure the Magic Link email
   template to include `{{ .Token }}` so recipients get the code they can enter
   in this app. Configure the SMTP sender, rate limits, abuse controls and OTP
   expiry for production. Set the site's production URL in Auth URL Configuration.
   This implementation uses typed OTP codes, with no redirect-token callback.
4. Ensure `public` is exposed in the Data API and the table has the grants in the
   SQL script. Do not remove row level security. Inspect Supabase security advisors.
5. Set these build-time deployment environment variables and rebuild/redeploy:

   ```text
   NEXT_PUBLIC_SUPABASE_URL=https://YOUR_PROJECT.supabase.co
   NEXT_PUBLIC_SUPABASE_ANON_KEY=YOUR_PUBLIC_ANON_OR_PUBLISHABLE_KEY
   ```

   These values are deliberately public. Never put `service_role`, an
   `sb_secret_` key, a database password or SMTP credentials in `NEXT_PUBLIC_*`.
   Local development can use HTTP `localhost`/`127.0.0.1`/`[::1]`; production
   requires HTTPS. URL credentials, paths, query strings and fragments are refused.
   Keep environment files out of git, as required by AGENTS.md.

## Behavior and recovery

- Email OTP creates an account for a new address. Signing in does not upload or
  import anything. The UI explicitly compares local and account cloud counts,
  differences and save time before offering upload, apply and delete.
- One snapshot per authenticated `user_id` is stored. Upload replaces the cloud
  snapshot only after confirmation; apply replaces matching local records and
  keeps local-only records, matching the existing JSON backup importer. Records
  include source drafts, notes, submissions, progress, preferences and supported
  practice modes. The shared backup validator is the allowlist and size limit.
- Apply requires first downloading a recovery copy when local records exist.
  Upload and delete offer a download of the previous cloud snapshot. Keep these
  files somewhere safe: they contain your practice data in plain JSON.
- Every update/delete filters the revision seen during comparison. First upload
  is INSERT (never an upsert). A unique-key race or zero returned rows is a
  conflict: both existing copies are preserved and another comparison is needed.
  Revisions and timestamps are regenerated by the server on every insert/update.
  Before applying data the client checks both the cloud revision and that local
  data still matches the comparison. No automatic conflict resolution occurs.
- Access tokens live in sessionStorage under a non-`ip:` key, scoped to the
  configured project origin; no refresh token is persisted. Session expiry or
  HTTP 401 requires signing in again. Backup export never includes auth tokens.
  Sign-out clears the local session even if the network request fails; an offline
  sign-out cannot revoke the remote token before its normal expiry. Closing a
  browser tab normally clears its session storage; browser restore behavior may
  vary, so explicitly sign out on shared devices.
- Delete removes only the current cloud snapshot after confirmation. It keeps
  local copies and the Auth account. Account removal is currently performed by
  the deployment owner through Supabase; deleting an account cascades its row.
- Snapshots are protected by TLS and per-user RLS, not end-to-end encryption.
  The project operator can access them. No admin keys are used by the app. Do not
  store credentials or confidential interview material in practice notes/code.
- A disabled provider, missing table, denied grants, network failure or exhausted
  quota surfaces an error and leaves local practice intact. There is no offline
  cloud write queue. Export JSON backups for independent recovery.
- The browser backup limit and database snapshot limit are both 20 MiB, but JSONB
  serialization and provider HTTP limits can reject a near-limit snapshot even
  when a JSON file export works. A rejected upload leaves the previous cloud row
  untouched; keep the local JSON export if a large snapshot cannot be uploaded.

## Required pre-release verification against the configured project

Automated tests mock HTTP; they do not prove the policies of a deployed database.
No live OTP emails or cloud writes were sent while building this feature.

Use two disposable email accounts A and B on a staging project:

1. Request and verify OTP for A; upload a small known snapshot and reload the
   settings page. Confirm session restoration and comparison, then sign out.
2. Sign in as B. Confirm A's row is absent. Using B's bearer token through a
   local REST client, explicitly select, PATCH and DELETE A's `user_id`; these
   must return no rows and leave A unchanged. INSERT with A's user ID must fail.
   Anonymous requests must not read or write the table. Do not paste tokens in
   issues, screenshots or logs. Never use a service-role token for this test.
3. As A, attempt to change `user_id` to B's ID; the UPDATE `WITH CHECK` must deny
   this. Confirm all four policies and RLS are enabled in the dashboard.
4. Compare on two tabs/devices. Upload in the first, then confirm an upload or
   deletion using the older comparison in the second. It must report conflict
   and keep both local data and the newer cloud snapshot.
5. Apply after making a local change in another tab; it must refuse and require
   a fresh comparison. Confirm a recovery file can restore the previous data.
6. Test expired/revoked tokens, storage denial, sign-out offline, wrong/expired
   OTP, rate limits, and a malformed cloud payload. Local practice must remain.
7. Test deletion, account switch, browser refresh and the no-env deployment.
